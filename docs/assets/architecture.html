LLM Observability — Architecture

You can't operate what you can't see. Instrument any LLM call to capture prompt, model, tokens, latency and cost as traces and spans, run online quality evals on sampled traffic, and drill into any request.

Six lines to instrument, then it is automatic

  • • a trace is one request; spans are its steps (retrieval, generation, tools)
  • • latency, tokens and cost are computed on span exit, not hand-written by the caller
  • • cost is tokens × per-model pricing, rolled up per trace
  • • a failed span marks the whole trace as error, so error rate falls out for free
  • • the core is stdlib + SQLite: zero dependencies to trace and store

Online evals on live traffic, not a separate offline run

  • • completeness, verbosity, toxicity and groundedness score sampled generation spans as they finish
  • • the evaluators are heuristic and key-free, so observability keeps working with no provider configured
  • • an LLM-as-judge evaluator drops in behind the same (span) -> {score, passed} signature
  • • demo traffic deliberately includes a refusal, an empty response, an ungrounded answer and a failed request, so the pass rates are non-trivial out of the box

What you actually look at

  • • overview: trace count, error rate, p95 latency, total and per-trace cost
  • • trace list with status, latency, tokens and cost, then drill into any span's input, output and eval scores
  • • the same numbers are readable over HTTP at /metrics, /traces and /traces/{id}
  • • honest caveat: offline the cost reads about $0 on mock pricing, and groundedness is lexical word overlap rather than an entailment model, so demo numbers are illustrative
